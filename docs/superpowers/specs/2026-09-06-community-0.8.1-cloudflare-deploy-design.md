# ProofClip Community 0.8.1 Cloudflare Deployment Design

**Status:** Design approved for specification review

**Date:** 2026-09-06

**Goal:** Make a clean ProofClip Community release deployable by a low-technical-skill user through one shared Cloudflare deployment flow without changing the 0.8.0 capture and delivery runtime.

## Product boundary

Community 0.8.1 is a deployment-layer release. It is not a feature release and does not change Capture, Archive, Field Mapping, Notion Delivery, Outbox, token encryption, D1 data semantics, or the privacy/non-retention behavior already accepted for Community 0.8.0.

The supported deployment topology is fixed:

```text
Chrome unpacked extension
        |
        v
Cloudflare Worker + D1
        |
        v
deployer-owned Notion OAuth integration
```

Cloudflare Pages is out of scope because the current Community repository has no independent web build chain and the Worker is the backend and OAuth/API origin.

## User contract

The ordinary deployer supplies exactly three values in a local, ignored `deploy.env` file:

```env
CF_API_TOKEN=
NOTION_CLIENT_ID=
NOTION_CLIENT_SECRET=
```

The deployer does not supply `CF_ACCOUNT_ID`, Worker name, D1 name or ID, Worker URL, API origin, callback URL, Extension ID, `TOKEN_VAULT_KEY`, or any environment label.

The supported user journey is:

```text
Download the clean 0.8.1 candidate
    -> copy deploy.env.example to deploy.env
    -> fill the three values
    -> run one deploy command
    -> add the printed callback URL to the same Notion integration
    -> load the printed configured extension directory
    -> Connect Notion
    -> choose a Data Source and run Set up ProofClip
    -> send one capture
    -> verify Delivery = SENT and Outbox = 0
```

The Notion callback save remains manual because the deployer must authorize and edit their own Notion integration. The deployer never sees or enters the stable public extension key.

## Stable Extension Identity Contract

The Community release manifest contains one stable public extension key. The key is release identity material, not a user credential.

Rules:

1. The public key is embedded in the official Community release manifest and may be distributed.
2. The corresponding private release material is never stored in the repository, candidate package, `deploy.env`, Worker configuration, logs, or browser extension source beyond the public manifest key.
3. The deploy core derives the Extension ID from the manifest key using Chrome's public-key identity algorithm and writes that derived value to the generated Worker configuration as `PROOFCLIP_EXTENSION_ID`.
4. The generated extension directory retains the same manifest key while its `COMMUNITY_API_ORIGIN` is patched to the newly deployed HTTPS Worker origin.
5. Community 0.8.1, later compatible Community updates, and the deployment doctor must treat the key and derived ID as one immutable identity contract.
6. Key rotation requires an explicit security incident or a separately approved breaking release. A normal upgrade must not rotate it.
7. The deployer must never load an RC, Commercial, rehearsal, diagnostic, or development extension directory as a substitute for the candidate's documented generated directory.

The contract removes the manual “find Extension ID, copy it, edit Worker config, redeploy” loop without weakening the Worker origin allowlist to accept arbitrary `chrome-extension://` origins.

## Deployment architecture

The implementation has one shared Node.js deployment core and two thin platform wrappers:

```text
deploy.ps1 ─┐
            ├─> deploy-core.mjs
deploy.sh  ─┘
```

The core owns all business behavior:

- environment loading and redaction;
- dependency and version checks;
- Cloudflare API token/account preflight;
- deterministic resource naming;
- ownership and conflict checks;
- generated staging tree creation;
- stable Extension ID derivation;
- Worker config generation;
- secure vault-key generation;
- secret writes;
- D1 schema/migration application;
- Worker bundle and deploy orchestration;
- extension-origin patching in the generated staging copy;
- health checks and final output;
- local deployment state persistence without credentials.

The wrappers only select the local runtime and invoke the core. They must not contain separate Cloudflare, Notion, D1, identity, or verification logic.

## Generated staging tree

The canonical candidate remains immutable during deployment. The core copies only the required extension and Worker source into an ignored generated staging directory, then writes all runtime-specific values there.

The generated tree contains:

- a configured unpacked extension directory;
- a generated Worker `wrangler.jsonc`;
- a generated Worker bundle;
- a non-secret deployment state record containing resource IDs, version, candidate identity, and derived Extension ID.

No secret, OAuth value, token, or private key may be written to the staging tree. The generated extension directory is the only directory the deployer is told to load in Chrome.

## Cloudflare preflight and resource contract

Preflight must complete before any create, update, secret write, D1 migration, or deploy action.

Required checks:

1. Node.js and a supported npm/npx runtime are available.
2. Wrangler is available through the package-local invocation path.
3. `CF_API_TOKEN` is present, non-empty, not Git-tracked, and never printed.
4. The token authenticates successfully against the Cloudflare API.
5. The token resolves to exactly one usable Account. Multiple accounts are an explicit stop condition unless the deployer selects one through a documented non-secret choice.
6. The token has the capability needed for Worker script deployment, D1 database management, and account discovery. A capability failure stops before resource creation.
7. Both Notion values are present and non-empty. Pairing with an integration is checked by the OAuth flow; the deployment layer never substitutes credentials from another environment.

Official resource names are deterministic for one account:

- Worker: `proofclip-community`.
- D1: `proofclip-community`.

The actual implementation must preserve the existing Worker binding name `DB`, compatibility date `2026-08-14`, `preview_urls: false`, and observability/logs enabled.

## Ownership and fail-closed rules

The deployer must not lose control of an existing account by silently reusing a same-named resource.

The core may reuse an existing Worker/D1 only when all of the following are proven:

- the local state record identifies the same resource IDs;
- the remote resource type and name match;
- the Worker configuration has the Community deployment marker and expected D1 binding shape;
- the candidate identity and deployment version are compatible;
- no conflicting callback, Extension ID, or D1 identity is detected.

If any check is unavailable or contradictory, the command stops with a human-readable `RESOURCE_OWNERSHIP_UNVERIFIED` or `RESOURCE_CONFLICT` result. It must not delete, rename, overwrite, or create a numbered fallback such as `proofclip-1`.

## Idempotency contract

The second execution against the same deployment must be safe and converge on the same Worker and D1 IDs:

- no second Worker;
- no second D1;
- no credential values printed or duplicated;
- no destructive schema reset;
- no duplicate migration side effect;
- one new Worker version only when the candidate or generated runtime actually changed;
- final health checks remain the same.

An existing state file is an optimization, not proof by itself. Remote ownership and configuration checks remain mandatory.

## Secrets and generated values

The deploy layer preserves the current Worker binding contract exactly:

- Worker variable `NOTION_CLIENT_ID` receives the public OAuth client identifier.
- Worker variable `NOTION_REDIRECT_URI` receives the derived callback URL.
- Worker variable `PROOFCLIP_EXTENSION_ID` receives the stable ID derived from the manifest key.
- Worker secret `NOTION_CLIENT_SECRET` receives the sensitive Notion credential.
- Worker secret `TOKEN_VAULT_KEY` receives the generated vault key.

The implementation must not move these values between `vars` and secrets as a convenience shortcut.

`TOKEN_VAULT_KEY` is generated from 32 cryptographically secure random bytes and Base64 encoded. Before the secret write, the core validates that the generated value is valid Base64 and decodes to exactly 32 bytes. The key value, prefix, suffix, hash, encoded value, and character data are never logged.

The callback is derived only after the actual Worker origin is known:

```text
https://<actual-worker-origin>/v1/auth/notion/callback
```

The exact same callback must be printed for the deployer to save in the same Notion integration and written into the generated Worker configuration.

## Deployment sequence

The only supported order is:

1. Validate the candidate manifest, provenance, and release boundary.
2. Load `deploy.env` without printing values.
3. Validate Node/Wrangler and Cloudflare Token capabilities.
4. Resolve exactly one Account.
5. Resolve or create the owned Worker and D1 resources under the ownership rules.
6. Create the ignored staging tree and derive the stable Extension ID.
7. Generate the Worker config with `DB`, compatibility date, preview setting, observability, Extension ID, Client ID, and the derived callback.
8. Generate and validate `TOKEN_VAULT_KEY`.
9. Apply the Community schema and privacy migration to the intended D1 with idempotent statements.
10. Bundle and deploy only the staged frozen Worker implementation.
11. Read the actual deployed Worker origin and patch only the staged extension copy's `COMMUNITY_API_ORIGIN`.
12. Verify `/privacy` HTTP 200, the OAuth route, the API route, the current Worker version, the D1 binding, and the generated extension path.
13. Print the Worker URL, callback URL, generated extension load path, and a redacted PASS summary.
14. Stop and wait for the deployer to save the Notion callback and complete the explicit OAuth/Data Source/capture acceptance.

No step may ask the user to edit source files, edit `wrangler.jsonc`, find an Account ID, create a vault key manually, or copy an Extension ID.

## Error handling

All user-facing failures use a stable code plus a short human explanation. Raw Wrangler stack traces are written only to a local ignored diagnostic log after redaction; secrets and authorization material are never written there.

Minimum failure codes:

- `DEPENDENCY_MISSING`;
- `DEPLOY_ENV_MISSING`;
- `DEPLOY_ENV_TRACKED`;
- `CLOUDFLARE_AUTH_FAILED`;
- `CLOUDFLARE_PERMISSION_FAILED`;
- `CLOUDFLARE_ACCOUNT_AMBIGUOUS`;
- `RESOURCE_OWNERSHIP_UNVERIFIED`;
- `RESOURCE_CONFLICT`;
- `NOTION_CREDENTIALS_MISSING`;
- `VAULT_KEY_GENERATION_FAILED`;
- `D1_INITIALIZATION_FAILED`;
- `WORKER_DEPLOY_FAILED`;
- `HEALTH_CHECK_FAILED`;
- `CANDIDATE_PROVENANCE_FAILED`.

The core fails before resource creation for missing/invalid credentials, token capability failure, account ambiguity, tracked `deploy.env`, candidate provenance failure, or ownership conflict.

## Clean candidate provenance gate

0.8.1 must be exported deterministically from the canonical source at the recorded commit. It must never be produced by patching an older RC/Fresh ZIP.

The release export must:

- bind the package to one source commit and one source provenance file;
- bind the Worker bundle SHA-256 to the release record;
- exclude `audit/`, `release/records/`, `release/artifacts/`, temporary diagnostic material, `.wrangler` caches, local runtime state, and any environment-specific Worker/D1/Extension identity;
- exclude RC, Commercial, Fresh rehearsal, and historical runtime identifiers;
- include the deployment template, schema, migration, deploy documentation, deploy entrypoints, and the exact `extension/src` load location;
- contain public placeholders only, never live secrets or OAuth material;
- pass a package-content scan before it can be handed to Jason.

The release record is the authority for candidate path, package SHA-256, bundle SHA-256, commit, and provenance match. A candidate that contains any old RC identity or acceptance/audit evidence fails closed.

## Implementation boundaries

The implementation plan may touch only these categories:

- `deploy/` for the shared core, thin wrappers, templates, tests, and examples;
- `.gitignore` for local `deploy.env` and generated staging/state paths;
- `extension/src/manifest.json` and focused identity tests for the stable public key contract;
- `extension/src/tests/` for identity and origin behavior tests;
- `release/` export/verification rules and release tests for clean candidate provenance;
- `README.md` and focused deployment documentation for the beginner path;
- `docs/` for the Cloudflare Token tutorial, deployment contract, and acceptance checklist.

The plan must not modify the 0.8.0 runtime algorithms or add Pages support.

## Verification strategy

### Unit and contract tests

- derive the same Extension ID from the manifest key across repeated runs;
- reject a missing, malformed, or changed stable key;
- validate HTTPS origin and exact no-trailing-slash normalization;
- generate and validate a 32-byte Base64 vault key without logging it;
- parse `deploy.env` without printing values;
- reject tracked `deploy.env`;
- render callback URL from the actual Worker origin;
- verify required Worker template invariants;
- verify no secret-like value enters generated config, logs, or package output.

### Mocked Cloudflare integration tests

- invalid Token stops before any create call;
- insufficient capability stops before any create call;
- multiple accounts stop or require explicit selection;
- existing same-named resources with unknown ownership stop without mutation;
- owned resources are reused on the second run;
- schema/migration calls are idempotent;
- Worker deploy and health-check failure produce stable failure codes;
- successful flow emits only non-sensitive final output.

### Candidate verification

- package SHA-256 matches the release sidecar and record;
- bundle SHA-256 matches the frozen record;
- source commit and provenance match;
- required files exist;
- RC/Fresh/Commercial/diagnostic identities are absent;
- audit/release evidence and local runtime state are absent;
- public placeholders are present where required;
- no real secret or token appears.

### Human release gate

Use a never-deployed Cloudflare account, a fresh Notion integration, and a fresh Chrome profile. The tester receives only the candidate and the beginner guide. The release passes only when:

```text
Candidate identity MATCH
Fresh Worker DEPLOYED
Fresh D1 READY
Extension loaded from documented generated directory
Extension ID BOUND
Notion OAuth PASS
Data Source PASS
One Capture PASS
Notion record CREATED
Delivery SENT
Outbox 0
/privacy HTTP 200
Second deploy reuses the same Worker/D1
Bad Token stops before resource creation
No developer intervention YES
No undocumented recovery YES
```

The two operational checks—idempotent second run and invalid-token preflight—are release gates, not optional doctor features.

## Non-goals

- No Pages deployment.
- No Vercel, Netlify, AWS, Azure, GCP, VPS, Docker, or Kubernetes official path.
- No Commercial integration or subscription behavior.
- No automatic Notion integration creation or callback mutation.
- No background capture or delivery.
- No source/runtime rewrite to remove the Worker Extension ID allowlist.
- No remote resource deletion or cleanup in the implementation phase.
- No tag, public release, or CWS submission as part of the deploy-layer implementation.

## Design verdict

`COMMUNITY_0.8.1_CLOUDFLARE_DEPLOY_LAYER_DESIGN`

The design preserves the accepted 0.8.0 runtime and addresses the actual deployment friction with one shared implementation, a stable hidden extension identity, deterministic resource ownership, idempotency, fail-closed behavior, and a clean candidate provenance gate.
