# ProofClip Community 0.8.1 Cloudflare Deployment Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a single, fail-closed Cloudflare Worker + D1 deployment layer that configures the existing Community runtime from exactly three user credentials and produces a generated extension with a stable internal identity.

**Architecture:** Thin deploy.ps1 and deploy.sh wrappers invoke one Node.js core. The core validates the candidate, authenticates and owns Cloudflare resources, renders an ignored staging tree, deploys the existing Worker/D1 runtime, patches only the staged extension origin, and prints a redacted handoff. A separate 0.8.1 export verifier packages only clean canonical source and excludes audit, release, rehearsal, and environment-specific material.

**Tech Stack:** Node.js ESM with built-in node:test, node:assert/strict, node:crypto, node:fs/promises, node:child_process, and fetch; pinned Wrangler invoked from deploy/node_modules; PowerShell 7; POSIX shell; Cloudflare REST API; Cloudflare D1 and Workers.

**Spec:** docs/superpowers/specs/2026-09-06-community-0.8.1-cloudflare-deploy-design.md

## Global Constraints

- Community 0.8.1 is a deployment-layer release and must not change Capture, Archive, Field Mapping, Notion Delivery, Outbox, token encryption, D1 data semantics, or privacy/non-retention behavior.
- The supported deployment topology is Chrome unpacked extension -> Cloudflare Worker + D1 -> deployer-owned Notion OAuth integration.
- Cloudflare Pages is out of scope.
- The deployer supplies exactly CF_API_TOKEN, NOTION_CLIENT_ID, and NOTION_CLIENT_SECRET in the ignored local deploy.env file.
- The deployer does not supply CF_ACCOUNT_ID, resource names or IDs, Worker URL, API origin, callback URL, Extension ID, TOKEN_VAULT_KEY, or an environment label.
- The public manifest key is release identity material; its corresponding private material must never enter the repository, candidate package, deploy.env, Worker configuration, logs, or extension source.
- Community 0.8.1 and later compatible Community updates must preserve the same public key and derived Extension ID; rotation requires an explicit security incident or separately approved breaking release.
- All Cloudflare API, D1, secret, bundle, and verification behavior lives in the shared Node.js core; wrappers contain no duplicate deployment logic.
- Existing same-named resources with unknown or contradictory ownership must stop with no mutation.
- The current Worker binding contract remains exact: DB, compatibility date 2026-08-14, preview_urls: false, observability/logs enabled, vars PROOFCLIP_EXTENSION_ID, NOTION_CLIENT_ID, NOTION_REDIRECT_URI, and secrets NOTION_CLIENT_SECRET, TOKEN_VAULT_KEY.
- TOKEN_VAULT_KEY is generated from 32 cryptographically secure random bytes, Base64 encoded, validated as exactly 32 decoded bytes, and never logged or persisted locally.
- 0.8.1 must be exported deterministically from clean canonical source; it must never be produced by patching an older RC/Fresh ZIP.
- The second deployment run must reuse the same Worker and D1; an invalid token must stop before any resource creation.
- No tag, public release, CWS submission, RC modification, Commercial modification, or production deployment is part of implementation.

The spec is kept as one implementation plan because the staging tree, resource ownership, stable identity, secret flow, and candidate provenance share interfaces and cannot be released independently without weakening the fail-closed contract.
